## Decisions

- The move step reuses `writeVersionAndOccurrence`: its occurrence update now also sets `path` to
  the written path, which is a no-op for rule 1 and the move for rule 2, so a moved occurrence
  gets the same version lookup, parent and reactivation logic as a rescan (FR-126-16, A13).
- The unseen occurrences are computed from the rows rule 1 already reads, with the same
  `unseenOccurrencePaths` as the SPEC-125 marking step, so the two can never disagree; the moved
  occurrence's new path is discovered, so the marking step leaves it alone without a special case.
- The read of the unseen occurrences' latest versions skips skills' file content (a SQL `case`
  returns `null` for `skill-md`, whose match hash is the content hash), so mass deletions of skill
  directories do not load their files (NFR-126-03).
- `matchMoves` returns the moves in the order of the new paths and is linear (maps, no sort); the
  database applies them in ascending path order, as `added` is sorted (FR-126-24).
- AC-4's "full check with Phase 3": one more database test shows that a move is never decided by
  slug or name, also with a same-named bundled example present.
- A Phase 1 test whose scenario (an identical nameless skill relocated to the root in one scan)
  is now a move keeps its intent with an updated expectation (lesson recorded).
